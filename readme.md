# Static website

A static site with a hand-maintainable content pipeline. Pages come from
markdown, from hand-written HTML, or (later) from the page builder app. The
whole site is generated by a single binary that needs nothing installed.

Design language taken from `inspiration/website_style.html`: oversized uppercase
mastheads, a chroma-spectrum accent gradient, film grain, hairline editorial
grids, and photographs that scale slightly on hover.

---

## Quick start

```bash
./site_generate            # build the site into _site/
./status_check.sh          # inspect the result, no rebuild
```

`site_generate` needs nothing installed — no Node, no npm, no Bun. Run it from
this folder (the one holding `site_settings.json`).

On Windows use `site_generate.exe` and `status_check.bat`.

To preview locally:

```bash
python3 -m http.server 8080 --directory _site
```

## Writing a page

Three ways, all sharing one URL namespace. The slug comes from the filename, so
`input_markdown/mountains.md` publishes as `/mountains.html`. If two inputs want
the same name the build warns and adds a suffix.

**Subfolders are allowed, and the folders become part of the URL.**
`input_markdown/travel/iceland.md` publishes as `/travel/iceland.html`, as deep
as you like. Folder names are normalised the same way filenames are, so
`input_markdown/My Travel/iceland.md` is `/my_travel/iceland.html`. This is what
makes a large collection of notes safe to publish: two notes can both be called
`index.md` as long as they are in different folders, and neither can take the
other's URL. `input_custom_html/` nests the same way. A post folder in
`input_custom_post/` does not — there, a folder *is* one page.

Everything in these folders publishes. There is no allow-list: every `.md` under
`input_markdown/` becomes a page, and every other file in a folder that holds one
is copied to the site beside it. The two exceptions are `draft: true` in the
front matter, which holds a page back along with the files beside it, and names
beginning with a dot — `.obsidian/`, `.trash/`, `.DS_Store` — which are skipped
so a note vault can be pointed at the folder without its machinery going public.
A symlinked folder is followed, so the vault can live outside the repository, and
a link that loops back on itself is reported rather than followed. Anything the
build declines to publish is named in the status check, so nothing disappears
quietly.

Every input starts with the same YAML front matter:

```yaml
---
title: Title of the page
date: 2026-09-03
image: /image/photo.jpg          # card thumbnail and Open Graph image
tags: [tag_1, tag_2]
description: Short summary, used for the meta description and search results.
draft: false
---
```

### 1. Markdown — `input_markdown/*.md`

The usual way. Markdown plus KaTeX, rendered to static HTML at build time.

- `$inline$` and `$$display$$` maths are typeset during the build. No KaTeX
  script is ever sent to the browser.
- Headings are demoted one level: a `#` in the body becomes an `<h2>`, because
  the YAML `title` is already the page's `<h1>`.
- Every heading gets an anchor and appears in the outline panel.
- `![alt](/image/x.jpg "Caption")` becomes a figure showing
  `/image_min/x_min.jpg` with the full-resolution file behind a lightbox link.
  All the images in one post share a lightbox group, so the arrows step through
  that post's pictures.
- **Images written on consecutive lines become one justified gallery.** Write
  two or more `![…](…)` lines with no blank line between them and they are laid
  out as a row that fills the column, each cell keeping its native ratio. Put a
  blank line between them instead and each one is its own captioned figure.
  A gallery cell carries no visible caption — it is cropped to the row and a
  caption would eat the picture — but its alt text and title still reach the
  reader as the lightbox slide's description and heading, so write them either
  way. On a phone the cells stack at full width, uncropped.
- **Video and audio use the same syntax.** `![Caption](/video/clip.mp4)` renders
  a `<video controls>` — markdown has no media syntax of its own, and without
  this it produced an `<img>` pointing at an `.mp4`, which is a blank box.
- **A note can keep its pictures in the folder beside it.** Write the path
  relative to the note — `![Caption](photo.jpg)`, or `![Caption](img/photo.jpg)`
  for a subfolder — and the file is copied to the site next to the page, gets a
  `_min` counterpart generated beside it like anything in `image/`, and reaches
  the reader with the same thumbnail, dimensions and lightbox an absolute path
  gets. Absolute paths into `/image/` keep working exactly as before; this is an
  addition, not a replacement.
  `.mp3`, `.wav` and friends become `<audio controls>`. A video picks up
  `clip_min.jpg` as its poster frame if that file exists. Both use native
  controls and `preload="none"`, so they cost nothing until played and work
  with scripting disabled. A media link written mid-sentence degrades to a
  plain download link rather than breaking the paragraph.

### 2. Hand-written HTML — `input_custom_html/*.html`

For pages the markdown pipeline cannot express.

- Start the file with `<!doctype html>` and it is published **verbatim**, front
  matter aside. You own the whole document.
- Start it with anything else and it is treated as a **fragment**, wrapped in
  the site layout — you get the nav, footer, fonts and stylesheet for free.

Either way the content is never run through a template engine, so a literal
`{{` or `{%` in your page reaches the browser as typed.

Add `data-gallery="name"` to the lightbox anchors in a section to make that
section its own slider; without it every image on the page ends up in one mixed
group and the arrows wander between unrelated sets.

**Start from [`input_custom_html/block_test_page.html`](input_custom_html/block_test_page.html).**
It contains every block type this site can render, each fenced with
`COPY FROM HERE` / `COPY TO HERE` comments. Copy a block, paste it into a new
file, add front matter, rebuild. `block_test_page_a.html` and
`block_test_page_b.html` show the two hero treatments.

### 3. Page folders — `input_custom_post/post_x/`

A folder holding `post_x.html` plus its own images and media. The HTML follows
the same doctype rule as above; everything beside it (except the `.json` save
file) is copied to `/post_x/`, so paths inside the page keep working. `_min`
counterparts are generated beside the originals rather than in a mirror.

This is the format the page builder app will read and write.
[`input_custom_post/post_i/`](input_custom_post/post_i/) is a working example —
page, save file, media and thumbnail.

### Drafts

`draft: true` keeps a page out of the build entirely — not merely unlisted; the
file is never written. Use `--drafts` to preview them locally:

```bash
./site_generate --drafts
```

> **A note on the spec.** `website.md` says *"If `draft = false`, the page is not
> generated"*, which is inverted from the usual meaning and would have hidden
> the one non-draft test post while publishing the two marked `draft: true`.
> This implementation uses the conventional reading: **`draft: true` is hidden.**
> Say the word if you want it the other way and it is a one-line change in
> `eleventy_binary/lib/eleventy_config.js`.

## Changing how it looks

Almost everything lives in **`css/theme.css`**. It is organised as tunable
tokens and nothing else in the project hardcodes a colour or a type size.

### Typography

Each font family has its own base size, letter-spacing and line-height, and the
whole site is derived from them:

```css
--font-text-root / --font-text-tracking / --font-text-leading    /* body copy */
--font-mono-root / --font-mono-tracking / --font-mono-leading    /* labels    */
--font-display-tracking / --font-display-leading                 /* mastheads */
```

Mathematics is deliberately **isolated** — KaTeX carries its own metrics, and
mixing it into the body scale pulls fractions and radicals out of alignment:

```css
--font-katex-root / --font-katex-tracking / --font-katex-leading
--font-katex-display-scale
```

`--font-katex-root` is set from a measurement, not a guess. Harald Revery Text
has an unusually small x-height (0.33em) while KaTeX_Math has 0.453em, so at
equal CSS sizes the maths rendered **45% larger** than the sentence around it
and visibly popped. At `0.80rem` inline maths sits ~3% off the prose x-height,
which reads as matched; display blocks carry `--font-katex-display-scale` on
top because they stand alone. Trust your eye over these numbers and adjust.

Both project fonts are single-weight 400. There is no bold, and
`font-synthesis: none` stops browsers faking one. Emphasis comes from size,
letter-spacing, case and colour instead.

**Optical centring.** These faces put their ink high in the line box —
uppercase caps measure 0.150em of space above but 0.384em below — so anything
the browser centres vertically *looks* pushed up. Two tokens correct it, applied
as asymmetric padding on buttons, chips, nav links and pagination:

```css
--optical-shift-caps: 0.086em;   /* uppercase Mono */
--optical-shift-text: 0.030em;   /* mixed-case Text */
```

Tune them by eye; set both to `0em` to see the uncorrected version.

### Colour

Light values sit on `:root`; dark values are redefined under
`@media (prefers-color-scheme: dark)`. Light and dark follow the operating
system — there is no theme toggle, by design.

`--fg-muted` and `--fg-faint` are set for WCAG AA (4.5:1) against both `--bg`
and `--bg-raised`, not chosen by eye: they carry dates, captions and outline
entries, which are content. Every text colour on the site was measured — if you
lighten them, re-check.

Components only ever reference the semantic tokens (`--bg`, `--fg`,
`--hairline`, `--panel-bg`, …), so a scheme change needs no component edits.
`--ink` and `--paper` are the exception: they are absolute and never swap, for
surfaces meant to stay dark in both themes (glass sections, the 404 stage, and
a hero laid over a photograph).

A plain `.hero-stage` is *not* one of those. It stands on `--stage-ground`,
assembled in section 6 from the three `--stage-1/2/3` stops each scheme
declares: a pale stage in light mode, the old matte in dark. Its type comes
from `--hero-fg` / `--hero-fg-muted`, which default to `--fg` / `--fg-muted`.
Adding `.hero-stage-photo` pins both back to light-on-dark and swaps the ground
for `--hero-scrim`, because over a photograph legibility is not always a matter
of preference. Retune the light stage by editing the three `--stage-*` values in
section 4 and nothing else.

`.hero-stage-photo-adaptive` is the other half of that pair: the same
photographic hero, but washed towards the scheme's own ground rather than always
towards black, with the type in ink or paper to match. It is what
`block_test_page_b.html` uses. Use one modifier or the other, never both — the
fixed variant pins several colours to `--paper`, including the two `.text-flow`
fallbacks, and a hero carrying both classes comes out paper on paper in light
mode. The two do not share an image opacity (0.50 dark, 0.72 light), for the
same reason the cinematic stage below does not: mixing a picture towards white
mostly flattens it, while mixing towards black darkens it fast. Reach for the
adaptive one whenever the photograph is quiet enough in its top third for ink to
hold over it, and for the fixed one when it is not.

A `.hero-stage` that is the first thing in `<main>` runs the full viewport
height and starts at the top of the document, with the sticky nav floating over
it. That is deliberate: when it started *below* the nav there was a hard
horizontal edge one nav-height down the page, and because the bar is
translucent that edge was visible sliding up through it on the first scroll.
The rule is scoped with `:first-child` so a hero used lower down a page does
not pull itself over whatever precedes it.

### The cinematic stage

`.cine-stage` is the other opening section: a film title card — a photograph, a
slow Ken Burns push, a grain overlay, and a title that develops out of blur one
letter at a time. It is what the front page opens with, and what
`block_test_page_e.html` demonstrates. It used to travel inside that page's own
`<style>`; it is a component in `main.css` now, because two copies of a block
that size drift apart the first time one of them is tuned.

It is not a `.hero-stage` and does not inherit from one. It declares the three
`--hero-*` tokens itself, which is the whole of what `.hero-scroll-cue` needs to
work over it — and because this card is centred rather than set left, the cue on
it carries `.hero-scroll-cue-center`, which pins both edges to the content column
and centres the label between them instead of parking it in the lower right. `nav_reveal.js` names it alongside `.hero-stage`, so a leading one
gets the same disappearing bar.

**It answers to the system colour scheme**, which is a departure from
`.hero-stage-photo` — that one pins itself light-on-dark because over a
photograph legibility is not a matter of preference. What lets this one differ is
`--cine-image-opacity`: the picture is not laid at full strength under a scrim,
it is *mixed into* the stage's own ground. Swap that ground for a pale one and
the whole frame goes pale with it, so dark type over it is as legible as light
type was over the near-black, and the vignette veils towards the same colour so
it still holds the edges back in both. Two channel triples carry the whole thing
— `--cine-ground` and `--cine-ink` — and every alpha in the block is written
against them, so the dark scheme is four declarations at the foot of the
component rather than a second copy of anything. The two schemes do not share an
image opacity (0.4 dark, 0.68 light): mixing towards black darkens the midtones
fast while mixing towards white mostly flattens them, so the value that reads as
a quiet ground on paper reads as an almost-empty frame in the dark.

**The frame dissolves into the page** over the last `--cine-fade` (30svh) of its
height. This is `.cine-stage::after` — one static gradient painted at `z-index:
3`, above the picture (0) and the grain (2), below the card and the cue (4), so
the type stays at full strength while everything behind it goes.

It was written with `mask-image` first, the way `.hero-stage` does it, and both
reasons it is not any more are worth knowing, because a mask is the obvious way
to write this.

**A mask is transformed along with the element it is on**, because it is part of
that element's own painting. `.cine-grain` is transform-animated — eight steps of
up to 94×76px, eighteen times a second — so its mask went with it. Measured with
the picture hidden and the noise at full strength, the grain surviving at a fixed
row swung by up to 50 levels between two consecutive steps and the fade edge moved
77px inside the visible frame: a band along the bottom of the hero flickering at
18Hz. A mask can only go on a layer that does not move.

**A masked ancestor takes descendant animations off the compositor in Gecko.**
Masking `.cine-media` put the 34s Ken Burns zoom on the main thread, re-rasterising
a 2800×1750 photograph every frame; masking the grain did the same to a
full-screen noise layer eighteen times a second. Both are pure compositor
transforms again now.

What a mask buys is not needing to know what is behind it. Here the backdrop is
`body`, which is a flat `background-color: var(--bg)` — so the gradient simply
ends *on* that colour. `--bg-rgb` (theme.css, tracking `--bg` in both schemes) is
what lets it also start on that colour at zero alpha; `transparent` would not do,
since it is `rgba(0, 0, 0, 0)` and on any engine that does not interpolate in
premultiplied alpha the fade runs through grey.

One trap worth knowing generally. `--cine-fade` is declared as `30vh` and upgraded
to `30svh` inside `@supports (height: 1svh)`, rather than as the two consecutive
declarations `min-height` uses a few lines above it. A custom property cannot use
that idiom: its value is an arbitrary token stream, so `30svh` parses everywhere
and only fails later, at each point of use, each of which then falls back to its
initial value. `@supports` is the only way to ask the question early enough.

The title's timing is the one part that lives in the markup: each letter carries
its own `--letter-delay`, and one rule reads it with
`animation-delay: var(--letter-delay, 0s)`. `index.njk` builds those spans from
`settings.name` against a fixed delay table, so the scatter is identical on every
build and the page stays static.

Two things about it are worth knowing before tuning it.

The grain's **rate** is the whole effect. The noise tile is 240px and the moves
are not multiples of it, so every step shows a completely different field — a
third of the pixels on screen change value on each one, which is exactly what
film grain is. Film does it 24 times a second, past the point where the eye
reads the changes as texture rather than as events. Run it at six a second, as
this did at first, and the canvas appears to flicker; it is eight steps over
0.44s now, about eighteen a second, which fuses. Slow it below about twelve a
second and the flicker comes back.

**There is deliberately no flash, stutter or lamp layer over the frame**, and
that is worth recording because a title card is exactly the block someone
reaches for one with. There used to be one: `background: #fff` under
`mix-blend-mode: overlay`, stepped through three stutters with `steps(1, end)`.
Measured with the grain switched off, it jumped the mean luminance of the frame
by +3.2, +2.3 and +1.2 levels at 0.60s, 1.25s and 1.38s, each for about 52
milliseconds, across 96% of the pixels on screen. Three things made it read as a
fault rather than as light. First, `steps(1, end)` gave every transition a binary
edge — a ramp reads as a change in light, a step reads as an event. Second, a
*white* source under `overlay` clips: overlay is hard-light with the layers
swapped, so for any backdrop above mid-grey the result is `1 − 2(1−b)(1−s)`,
which with `s = 1` is exactly 1.0 whatever the backdrop was — the bright centre
of a photograph blown out completely, which is precisely where the title sits.
Third, it covered the whole frame, and a global luminance step is far more
visible than a local one of the same size. A smooth warm swell was tried in its
place and did not earn the layer it cost.

The frame's overall weight is one token instead: `--cine-image-opacity` on the
section, which mixes the photograph into the stage's own `#07070a`. That is not
the same move as more scrim, and the difference is the reason it is the knob.
Scrim is a veil laid *on* the picture: it lifts the blacks towards the veil's
colour and flattens the whole tonal range. Opacity mixes the picture *into* the
ground: the blacks stay black and the highlights come down. On a frame whose
problem is bright cloud rather than an over-light ground, the second is the one
that wants turning.

The defaults are tuned for the front page: a photograph that is mostly bright
cloud has to come back a long way before an eyebrow at 86% opacity will sit on
it. A page whose picture is already dark sets its own on the section and changes
nothing else — `block_test_page_e.html` runs its mist at `0.8`:

```html
<section class="cine-stage" style="--cine-image-opacity:0.8">
```

An inline style cannot be scheme-conditional, so a value set that way is used in
both. Fine for a photograph that reads at one exposure either way; a picture that
needs a different weight per scheme wants a rule rather than an attribute.

The column of type inside it is `.hero-copy`, and the row of buttons under that
is `.hero-actions`. Both used to be inline `style` attributes repeated on every
hero page; they are classes now for one reason, which is that an inline style
cannot be reached by a media query and the vertical rhythm of that column is
most of what decides whether a hero fits on a phone. The three gaps are custom
properties (`--hero-copy-gap-1/2/3`) so the blocks under **Breakpoints** below
retune all of them at once. A `<br class="hero-break">` in the headline is a
line break that only survives where there is room for one.

### The hero entrance

A leading hero is above the fold by definition, so its elements arrive on load —
one beat apart, no scroll trigger and no script. The whole mechanism is one
keyframe, a unitless beat number in a custom property, and a `calc` turning that
number into a delay:

```
delay = --entrance-lead + --hero-in-beat × --entrance-step
```

All five knobs live in `theme.css` section 6 (`--ease-entrance`,
`--dur-entrance`, `--entrance-lead`, `--entrance-step`, `--entrance-rise`, and
`--entrance-settle` for the one photographic move), so retuning the rhythm of
every hero on the site is one edit there.

Nothing is written on the markup. `:nth-child` rules on `.hero-copy` assign the
beats in source order, and the button row is skipped so its buttons continue the
count individually. For an element those structural rules cannot reach —
variant D's hung portrait, its plate caption, its engraved line — there is a
`.hero-in` utility that takes the beat inline:

```html
<div class="hero-in" style="--hero-in-beat:2">
```

Only `opacity` and `transform` are animated, which is what keeps a six-element
hero cheap on old hardware: both are compositor properties, so nothing here
lays the page out again on a frame. The rise is a transform rather than a
margin for exactly that reason.

Put `.hero-in` on a **wrapper**, never on an element that carries a transform of
its own. The animation ends on `transform: none` and holds it, so it will
quietly flatten an offset — which is why variant D animates the wrapper around
its hung frame rather than the mount that sits behind it.

The collage is the one hero that does **not** take its beats from source order.
Source order there begins with a portrait, and a photograph that size arriving
before the masthead is a hero that opens with a picture and then explains
itself. Its pieces are named rather than counted, so the numbers in `input.css`
*are* the running order: panel first, its type settling into it as it lands,
then portrait, landscape, ink block, stamp, and the ruler last. It also runs a
slower beat and a longer travel than the other heroes, set on `.collage` so
everything inside it moves at the same tempo and none of it reaches the heroes
meant to stay brisk.

The ruler is the one element that is *drawn* rather than faded — a `clip-path:
inset()` wipe from the left edge. A `scaleX` would have been the obvious choice
and is the wrong one: the track is a row of segments with gaps cut out of it,
and scaling stretches those gaps open as it grows, which reads as a rubber band
rather than a line.

### The post masthead

Markdown posts open with a header rather than a hero, and it takes the same
entrance: `post.njk` carries `.post-header`, and its five blocks — date, title,
lede, tags, rule — arrive one beat apart in source order at the site's default
rhythm. The gradient rule at the foot is drawn with the same wipe that closes
the collage; it runs two animations at once, the `flow` pan it already had plus
the draw, written out in full because the shorthand would otherwise drop the
first.

The body picks up where those five beats leave off, so the article assembles in
one movement from the top down. It is **two rules, not one per paragraph**, and
the cost is fixed at seven animations however long the post is:

| | |
|---|---|
| `.post-body .prose` | the whole body, fading up as one — covers everything, including the part below the fold |
| its first six blocks | a rise on top of that fade, on their own beats |

Both halves of that are deliberate. Posts here run from fifteen top-level blocks
to a hundred and one; give each its own animation and the browser promotes each
to its own compositing layer, and a long post with figures in it allocates a
hundred textures at load — a hitch on exactly the hardware the rest of this
stylesheet is careful about. A stagger long enough to *reach* the hundredth
block is also a reader waiting for text already on their screen.

So the fade is one element and is over inside two seconds, well before anyone
can scroll to the end of it, and the stagger is spent only on what a reader is
plausibly looking at. The six blocks rise with **no fade of their own** — the
parent is already carrying the opacity, and animating it on both would multiply
the two curves together and make the child arrive later and muddier than either
says. That is what `hero-in-rise` is for.

No script is involved in any of it. Nothing waits on a scroll position, so
nothing is ever left hidden behind an observer that did not fire.

### Browser support

The stylesheet deliberately avoids recent CSS. Transforms use `transform`
rather than the standalone `translate`/`scale` properties, offsets use
`left`/`right` rather than `inset-inline`, and there is no `@container` or
`text-wrap: balance` anywhere. `:has()` is the one exception and it appears
three times — the nav toggle twice, the width-cycle focus rule once — each
written so a browser without it loses that one behaviour and nothing else. The
collage hero used to be a fourth, reaching for `:has()` to find its own shell;
the shell carries a `.collage-shell` class instead. Cascade layers and `@property`
come from Tailwind v4 itself and are the only modern requirements.

Two exceptions, both written to degrade rather than break. `mask-image` draws
the hero's bottom dissolve and the editorial grid's fade; a browser without it
shows a hard edge instead of a soft one, and nothing moves. (The dissolve is a
five-stop ease rather than a straight ramp — over a fade this long a linear
gradient leaves a visible corner where it starts, which is the one edge the
section exists to avoid.) And `.hero-stage`
declares its height twice — `100vh` first, `100svh` second — so a browser that
does not know the small-viewport unit drops the second line and keeps the
first, which is only wrong by the height of a mobile URL bar.

The hero entrance holds its elements at `opacity: 0` through their delay, with
`animation-fill-mode: both`. That makes an animation load-bearing for
visibility, so every way it can fail was written to fail *visible*:

| | |
|---|---|
| no custom properties at all | the whole `animation` declaration is dropped at parse time — the hero is simply there |
| a malformed beat | `animation` becomes invalid at computed-value time and resolves to `none` — same outcome |
| `prefers-reduced-motion` | the block at the foot of `input.css` zeroes every delay site-wide, and switches these animations **off** rather than collapsing them — a 0.001ms animation still paints its 0% frame, and for these that frame is `opacity: 0` |
| printing | the print block drops animations outright, so nothing prints blank |

Opacity is never declared outside the keyframes, which is what makes all four of
those land on "visible" rather than on an empty stage. The delay is the one
people leave out: collapsing the duration alone leaves a wait with nothing at
the end of it, spent at `opacity: 0`.

`.text-flow` has a matching trap and a matching hook. It gradient-clips its
fill and has two fallbacks to solid ink — an `@supports` guard for a browser
without `background-clip: text`, and the reduced-motion block. An inline
`background-image` on the span outranks both, so a re-inked headline would
paint the gradient back in as a solid rectangle behind black type in exactly the
two situations meant to be safe. Re-ink through the custom property instead and
the fallbacks work as written:

```html
<span class="text-flow" style="--flow-image:var(--grad-heat)">gilded light</span>
```

### Breakpoints

The mobile/desktop cutover is defined once, in `css/input.css`:

```css
--breakpoint-md: 48rem;   /* below this is "mobile"; at or above is "desktop" */
```

The hero is the one component that also answers to viewport **height**, because
it is the one component asked to fit inside the screen rather than to flow down
the page. Three thresholds, all in the hero section of `css/input.css`:

| threshold | what it does |
|---|---|
| `48rem` wide **or** `43rem` tall | shorter dissolve, tighter top pad and copy gaps; the lede and buttons step down by width |
| `38rem` tall *and* narrow | the lede steps down again — for a 375x553 phone |
| `30rem` tall | the display headline sizes off the height and `.hero-break` is dropped, so the masthead reflows — a phone on its side |

The collage hero on `another_test_page.html` is the exception that gets a
different *composition* rather than a tighter one. Below `48rem` — or on
anything under `30rem` tall — the portrait plate leaves the flow and becomes the
hero's ground, the glass panel is the only piece left standing on it, and the
second photograph, the ink block, the date stamp and the ruler are dropped.
Stacked at any height that did the photographs justice those five pieces ran to
1552px on a 390x664 screen, and to 1281px on a phone turned sideways; as one
picture with the masthead over it the hero is exactly one screen at every size,
and the picture is larger than it has ever been in that block. Nothing dropped
is unique to the hero — the landscape frame and Plate 001 both appear again in
the plates section below it. Between `48rem` and `60rem` the five pieces still
stack, which is the layout that band has always had.

They exist because a leading `.hero-stage` is `min-height: 100svh`, so it can
only ever be *taller* than the screen if its own contents make it so — and they
did, on every hero page here: +55px at 390x664, +186px at 375x553, +216px at
844x390. The scroll cue sits on the hero's bottom line and was off the bottom of
the screen on all of them. Nothing above 43rem tall and 48rem wide is touched by
any of it; a 1440x900 hero measures the same to the pixel as it did before.

## JavaScript

The site ships **four** scripts, all local, all optional, all deferred:

| File | What it does |
|---|---|
| `javascript/search_bar.js` | Search field in the nav, with a suggestion dropdown and arrow-key navigation |
| `javascript/reading_width.js` | Cycles the post column through 100 / 75 / 55 / 40 / 28 / 18 %, remembered in `localStorage` |
| `javascript/nav_reveal.js` | On a page that opens with a full-height hero, keeps the bar out of the way until about half a viewport down. One `IntersectionObserver`, two classes on `<html>`; the reveal itself is CSS. It looks for the opening sections named in its own `LEAD_SECTIONS` — `.hero-stage` and `.cine-stage` — at the top of `<main>`, skipping any `<style>` a self-contained block brought with it. Every width, phones included — which means the menu button goes with the bar, and a phone reader on a hero-led page has no navigation until they scroll. That is deliberate; `:focus-within` and `:has(.nav-toggle:checked)` are what keep it from being a trap, and neither may be dropped. |
| `javascript/glightbox.min.js` + `glightbox_settings_min.js` | Image lightbox and slider, restyled to the site's fonts and palette. The panel stays dark in both schemes: a photograph is judged against a neutral ground, and a light caption bar under a dark scrim reads as a mistake. |

**With scripting disabled the site is complete.** The search field and the width
control are `display: none` until their own script marks `<html>`, so they are
absent rather than visible-and-dead. Everything else is CSS only:

- the mobile navigation drawer (checkbox + sibling selector)
- the post outline panel, and jumping to a heading
- tag filtering (one page per tag, generated at build time; the chip list
  collapses to two rows past 12 subjects, with a checkbox to expand)
- pagination
- FAQ accordions (`<details>`)
- card and row hover effects

KaTeX is typeset during the build, so mathematics is fully rendered with no
script at all.

The two stylesheets and two scripts that only some pages need are added
automatically, based on what each page's markup actually contains — you never
set a flag. See `eleventy_binary/lib/assets.js`.

Vendor stylesheets are injected **before** `main.css`, deliberately. GLightbox
styles `.gslide-title` at exactly the specificity anyone would use to override
it, so load order is the only thing that decides the winner — get it backwards
and the lightbox keeps its default Arial-on-white look.

Pages also carry a `<script type="application/ld+json">` block of structured
data. That is a data block, never executed, so it does not breach the no-JS
rule; it is what lets a search result show the author, date and image.

## Images

`image_min/` mirrors `image/`, subfolders included, holding a compressed
counterpart of every photograph. Galleries, cards and post figures load the
counterpart; the full-resolution file is only fetched when a lightbox opens.

You can maintain `image_min/` yourself. If a counterpart is missing the build
generates one and **tells you it had to**, so you can replace it with your own
compression and keep builds reproducible. Post folders keep their counterparts
beside the originals rather than in a mirror.

Generated counterparts are held under 80 kB. Quality is stepped down first, and
if that is not enough the image is scaled down (1600 → 1280 → 1024 → 800 px on
the longest side) — an oversized thumbnail defeats the point of having one. If
an image resists even that, the build says so and you should supply your own.

**`card_thumbnail/` is different.** Images there are already thumbnails, so they
are used exactly as written and no `_min` counterpart is looked for. The same
goes for `svg/` and `gif/`. Thumbnail resolution checks the filesystem rather
than rewriting paths blindly, so a front-matter `image:` never points at a file
that was not generated.

Every `<img>` is emitted with `width` and `height`. That is not decoration: it
reserves the right space so the page does not jump on load, and it stops
`loading="lazy"` deadlocking on an image whose height would otherwise collapse
to zero and never enter the viewport.

### What every picture carries

Markdown gets this for free — `renderFigure()` in
`eleventy_binary/lib/markdown.js` fills all four in from
`![alt](/image/x.jpg "Title")`. In hand-written HTML you write them yourself,
and all four earn their place:

| | |
|---|---|
| `alt` on the `<img>` | What the picture shows. Read aloud by a screen reader, and the strongest signal image search has. Not a copy of the caption — that reads the same words out twice. |
| `<figcaption>` | The visible caption. A `<figure>`/`<figcaption>` pair is the markup that says this text belongs to this image, and text beside an image counts. |
| `data-title` on the lightbox link | The heading on the slide. |
| `data-description` on the lightbox link | The line under it. Set from the alt text, so the slider says the same thing the page does. |

`width` and `height` are the real pixel dimensions of the file in `src` — the
`_min` counterpart, not the full-resolution file the lightbox opens. Get them
from `identify -format "%w %h" image_min/….jpg`; a ratio that does not match the
file reserves the wrong shape and the page jumps anyway.

`block_test_page.html` is the worked example: the waterfall gallery fence spells
all of this out beside the markup it applies to.

## Settings

`site_settings.json` holds the name, short name, description, URL, language,
posts per page, navigation (label, link, order), default image, the folders
copied into the site, and the asset size budgets the status check enforces.

`language` is the two-letter code that goes into `<html lang>` and the feed.
`date_locale` is separate, and is the full BCP-47 tag used to render dates on
the page — `en-GB` for "9 September 1999", `en-US` for "September 9, 1999". A
language code alone does not determine a date order, so the two are not derived
from each other.

`asset_folders` is the list of directories copied verbatim into `_site/`. Add
your own — `photos/`, `sketches/`, whatever — and it is a settings change rather
than a code change. A folder listed but not present is reported as a note, not
an error.

It ships with `SITE_NAME` and `https://example.com` placeholders. Fill them in
before publishing — the URL drives the sitemap, the RSS feed and every Open
Graph tag.

## Checking the site

```bash
./status_check.sh
```

Reports broken local links, images with no alt text, missing `_min`
counterparts, oversized assets, missing or malformed front matter, duplicate
slugs, missing meta descriptions, and anything that reaches outside your own
domain. Exits non-zero on errors, so it can gate a deploy.

The same findings are written to **`_site/status_check.html`** — open it
directly in a browser after a build. It is not linked from anywhere and carries
`noindex`.

## Layout

```
input_markdown/       markdown posts; subfolders become URL folders
input_custom_html/    hand-written pages, incl. the block test pages

card_thumbnail/       blog card thumbnails (already sized; not mirrored)
font/                 Harald Revery Text & Mono, plus the KaTeX fonts
svg/ gif/ video/ audio/ icon/
licence_and_legal/    legal.md plus every bundled licence -> legal.html
eleventy_njk/         page templates
eleventy_settings/    layouts and partials
eleventy_binary/      the generator, and the script that compiles it
_site/                generated output — never edit by hand
```

`_site/` is deleted and rebuilt on every run, so a page you renamed or a draft
you previewed does not linger and keep being served.

## Development

npm is a development convenience only. **Site generation never touches
node_modules** — that is what the binary is for.

```bash
bun install                        # once
bun run build                      # same as ./site_generate
bun run build:drafts               # include drafts
bun run css:watch                  # rebuild CSS on change
bun run vendor                     # re-copy KaTeX + glightbox into the repo
./eleventy_binary/compile.sh       # rebuild site_generate and site_generate.exe
```

See [`eleventy_binary/readme.md`](eleventy_binary/readme.md) for how the
generator is put together and how the binary is produced.
